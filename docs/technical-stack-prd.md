# Vibe Keyboard 技术栈与架构 PRD

状态：原型实施基线，待实机验证

2026-11-10 工程补充：一期范围及硬件冻结条件见[硬件实施规范](phase1-hardware.md)，执行与进度唯一清单见[一期 Stage Spec](phase1-tasks.md)。一期为 S0、S1 加完整有线整机交付，不要求先完成 S2 三模；S3 仍指后续首发工程样机。以下三模内容为后续设计目标，不能阻塞一期有线闭环。

产品需求与键位：[产品定义白皮书与 BRD](Vibe-Keyboard-BRD.pdf)

## 1. 范围与成功标准

有线原型先验证 Windows 上的完整链路。两项 Claude Code 任务并行，方屏显示当前待办，用户按大键回到屏上会话。首发硬件目标为 USB-C、2.4G 接收器、BLE 三模。三种模式都必须支持基础按键、方屏状态回传和大键定位，按住说话列入首发功能计划，使用电脑或耳麦，在核心闭环通过后实施和单独验收。设备运行时只选择一个连接模式和一台控制主机。

首轮固定 Windows 11、桌面版 VS Code、原生 Windows Claude Code CLI 的受测版本。先支持由扩展启动的内置终端。其他 IDE、外部终端、WSL／SSH 和任意已运行终端的自动接管后续按证据扩展。首件以静态状态卡和按需局部刷新为基线。桌宠动画、网页直连、云同步、无线 OTA 和板载麦克风另行排期。

## 2. 技术选型

| 层 | 选型 | 使用边界 |
| --- | --- | --- |
| Windows 上位机 | C#／.NET 10 LTS，CLI 起步，功能通过后加 WPF 托盘与设置界面 | 单进程维护会话、待办、设备连接和映射。USB 使用 Windows HID 接口，BLE 使用 Windows GATT API。配置用本地版本化 JSON，原子替换并保留可恢复的旧版。 |
| Agent 与 IDE 适配 | Claude Code Hooks ＋ TypeScript VS Code 扩展 | Hook 回报会话事件，扩展持有 Terminal 对象。Windows 前台激活单独验证。 |
| 有线固件 | Pico 2（RP2350）、Pico C/C++ SDK、TinyUSB、CMake／Ninja | 首购用已焊排针版本，先实现键盘 HID＋厂商 HID 和 SPI 局刷。已有 RP2040 仅作早期验证；最终换板须重验。官方 Pico 2 板载口为 Micro-USB，不能当作 USB-C 整机直接交付；一期载板与数据转接见硬件规范。原型板不作为量产料号。 |
| 三模固件 | nRF52840 模组优先候选，nRF Connect SDK（Zephyr）、C、west／CMake | 键盘与接收器独立固件，共用协议与测试向量。BLE 用 HOGP＋自定义 GATT；2.4G 优先验证 ESB 双向链路。用锁定版本的实际样例验证 USB 复合设备、BLE 和 2.4G 后再确认模组。 |
| 方屏 | 带显存、像素数据走 SPI、支持窗口局刷的方屏 | 一期采购基线为微雪 1.54inch LCD Module、240×240、ST7789、非触摸 SPI 模组，采购前复核版本与预焊接口。约 2.1 英寸是后续外观目标；未锁定料号不得据此开板。SPI＋RGB 配置接口不等于像素可走 SPI。屏幕缓冲按行或区域分配。 |
| 语音（首发跟进） | Windows WASAPI 采集，本地 whisper.cpp 为首轮候选 | 用中文及中英混合实测延迟和可用性。先支持预览与复制，验证目标能安全接收文本后再开放插入。语音模型由电脑运行。 |
| PCB 与结构 | KiCad 10＋kicad-cli 为默认交付工具 | 自研默认使用 KiCad 10。国内打样外包可采用合作方熟悉的嘉立创 EDA Pro，报价时确认可重新打开编辑的原生工程和工具版本。先拿屏幕规格书和实物，再冻结接口、结构堆叠及 PCB。 |

## 3. 架构与职责

    Claude Code Hooks ── 会话事件 ──► Windows 上位机
    VS Code 扩展 ◄──── 会话绑定与聚焦 ────► Windows 上位机
    Windows 上位机 ◄── 按键事件／状态快照 ──► 键盘
                USB 直连 | USB 接收器＋2.4G | BLE GATT

- **Windows 上位机拥有业务状态。** 同一串行状态处理路径维护待办、会话绑定和设备屏幕快照。按首次阻塞时间排序并按会话去重。选中项解除后回到队首。失联或证据不足时显示不可用。每种连接各有适配器，队列与业务规则共用。
- **扩展拥有终端实例。** 由扩展命令启动 Claude Code，在启动环境中注入本次会话绑定 ID。Hook 转发器携带绑定 ID 与 Claude Code session ID 上报。用进程或扩展实例的生命周期清理绑定。窗口句柄、终端对象任一失效时要求重新绑定。工作区名、终端标题仅供显示。S0 先用用户主动执行的窗口绑定命令，在该窗口仍处于前台时采集 HWND，同时核对 VS Code 进程归属和扩展的窗口焦点状态。最小化恢复、窗口重建与句柄复用纳入验证。
- **固件负责输入和显示。** 扫描、去抖、旋钮／摇杆仲裁、标准按键、状态卡和离线页留在设备端。渲染使用有界缓冲，局刷不能阻塞输入。接收器只做数据转发与标准 USB HID，业务状态仍由电脑管理。
- **先共享契约，再共享实现。** Pico 与 Nordic 各自接入本平台驱动。协议、测试向量和键位语义先共用，固件中已稳定的纯逻辑可迁移，避免为两个 SDK 提前搭建完整硬件抽象层。

## 4. 关键流程与故障处理

### 待办状态与精准回跳

1. 先在锁定版本记录脱敏 Hook 事件样本，覆盖等待权限、处理完成、取消、错误和退出。用实际观察确定状态转换。没有明确解除证据的事件保持未知或过期。普通工具权限请求优先验证 `PermissionRequest`，`Notification(permission_prompt)` 用于补充和去重。官方文档说明普通权限提示的通知可能在等待约 6 秒后才触发，该路径单独计量，不能代替实时信号达标。`PreToolUse` 发生在工具执行前，单独出现不代表正在等用户。用 `PostToolUse`、`PermissionDenied`、`Stop`、`SessionEnd` 等事件按实测证据更新状态，避免用无关工具的完成事件清掉待办。转发器优先使用锁定版本支持的异步 command hook，通过当前用户限定的 IPC 限时上报，不返回授权决定。测试上位机退出、管道不可用及背压时权限流程仍可继续。记录启动到上报耗时，按实测定超时。
2. 上位机将可见卡片和当前大键映射打包成快照。固件完成显示后更新可交互的快照版本。按大键时回报该版本。电脑仅允许跳到这个版本绑定的有效会话。待办已解除、映射变更或版本过期时提示刷新，避免错切。
3. Windows 请求激活已绑定窗口，扩展对目标调用 `Terminal.show(false)` 并回报实际选中的终端。上位机核对前台窗口和扩展回执。Windows 拒绝激活时通知用户点击激活，再校验目标。重复按大键仍只定位，批准或取消由用户在原会话完成。

**事件语义补充。** `PermissionDenied` 不能用作通用的“用户点击拒绝”信号；当前官方说明仅覆盖 auto mode 的特定拒绝。用户拒绝、Esc、提问等待、工具失败与会话退出分别采样，记录所用版本实际提供的证据。无法可靠识别解除时让条目过期并禁止操作，不能用不相关的 `PostToolUse` 清除。异步 Hook 的传输器自行限制运行时长，不能假设配置中的 timeout 一定终止后台进程。

### 编码层复制键

R4C2 默认复制，R5C2 默认粘贴。在受支持的 VS Code 终端使用仅复制选区的动作，无选区时不触发终端中断。通用前台编辑器按标准复制处理，无法辨别终端上下文时提示或要求用户显式改绑。首件验收覆盖编辑器复制、终端有选区和终端无选区三种情况。

### 本地通信（S0）

Windows 上位机以当前用户权限监听命名管道。原生 VS Code 扩展通过 Node.js IPC 建立长连接，每个窗口实例独立登记，并提交它实际管理的终端绑定 ID。上位机按窗口实例和终端绑定 ID 路由，聚焦请求使用关联 ID 对应回执。断线清除旧路由，重连重新登记，超时或回执不符时停止。Hook 转发器用同一管道的独立短连接上报事件，不能请求窗口聚焦。首轮以同一 Windows 用户和普通权限运行上位机及 VS Code。

### 语音（BR-05，P1 首发跟进）

S1 通过后开发，保留语音键位。该功能单独验收录音、转写预览、复制、安全插入及断线停止，并在首发前验收计划中的各连接模式。S0 和 S1 放行以方屏待办与会话跳转为准。

语音键按下时固定目标，松开时停止录音并打开可编辑预览。插入前重新校验会话和输入状态。只允许插入审阅后的文本，提交由用户操作。权限确认、工具执行中或输入状态未知时只提供复制。目标失效或适配器未通过插入测试时保留文本并提供复制。拔线、切模、断连或丢失松开事件时停止录音，录制设时长上限。默认音频和转写不写入诊断日志。

### 连接与协议

- 业务消息基线为 `HELLO`、`STATE_SNAPSHOT`、`STATE_APPLIED`、`INPUT_EVENT`、`ACTION_RESULT`、`HEARTBEAT`。会话键使用短期 opaque token，项目名长度有上限。设备只接收必要状态，无需提示词、目录绝对路径、录音或 Agent 凭证。
- 方屏首版接收结构化状态快照，包括项目短名、状态、队列序号、数量和大键映射，固件本地绘制固定布局。固定中文状态词用内置字形，项目短名可配置。遇到缺字使用受支持的短名或稳定会话代号，并验证不同会话显示可区分。字库和可见字符按屏幕实测扩展。
- 连接握手交换协议主版本、能力和连接代次。每条业务消息有序号。输入事件带当前快照版本，重试按连接代次与序号去重。状态按最新完整快照恢复，过期动作丢弃。跨重连禁止重放用户动作。
- USB 直连和接收器均提供标准键盘与独立厂商通道。BLE 基础按键走 HOGP，自定义服务独立承载应用消息，写入和通知需在授权连接中验证。传输适配器根据实际报告长度、ATT MTU 或空中载荷分帧。有界重组并测试分片缺失、重复、超时和超长输入。
- 2.4G 首轮验证键盘主动上报、接收器通过 ACK 载荷或明确的应答机制下发。无按键时也要按实测确定接收窗口，使状态可以更新。链路层确认与设备已经应用状态分开记账。协议、认证、加密和防重放在发售前评审，接收器只接受已配对设备。BLE 与 2.4G 按模式互斥启停。
- 模式切换时在可用的旧链路发送释放报告，再清理旧连接。接收器失联时也要主动向电脑发送释放报告。完成新握手和全量同步后恢复业务按键。桌面端退出后，基础键盘继续工作，方屏超时转为离线。

### 无线供电、显示与堆叠

- 无待办时评估按空闲时长调暗或息屏。无线链路可用时，收到新的确认或失败状态后恢复背光。2.4G 依靠键盘周期接收窗口或轮询获得下行状态，BLE 按连接策略接收更新。断链或关闭无线电的深度休眠靠本地操作恢复，再重新同步。先用 S2 同时测亮屏、低亮、息屏、空闲接收及重连的电池端电流和上屏时延，再冻结亮度、超时、轮询和容量。
- nRF52840 有 256 KB RAM。三模原型继续采用行缓冲或小区域刷新，在锁定 SDK 和实际屏上测静态占用、栈峰值及刷屏与无线并发。SPI 速率按屏模组、布线和实测选定，首发基线为静态状态卡。
- 三模结构另做堆叠：电池和固定件、充电与保护及供电路径、可触及的模式开关或等效实体入口、天线净空和接收器。金属方案评估非金属射频窗口或非金属外壳工艺，天线位置按模组参考布局与装壳实测确定。
- 三模询价按键盘加接收器成套拆价，分别列主板和天线、电池和电源、模式开关、接收器 PCBA 与外壳、烧录配对和产测。一次性工程及模具费用单列。

## 5. 阶段与验收

以下为验收门槛或试验口径。实测报告记录软件版本、硬件料号、测试环境、样本数及失败原因。

| 阶段 | 可开始的工作 | 放行条件 |
| --- | --- | --- |
| **S0 Windows 验证** | 现成键盘触发 CLI、扩展管理两个会话、模拟方屏输出 | 同窗口双终端和不同窗口各连续轮换 20 次，覆盖浏览器前台、最小化、重名和会话退出。零错跳、零误提交。激活受限单独计数，报告自动成功率、人工点击次数及耗时。两组预设常用路径自动成功均须至少 18／20，人工兜底不计入自动成功。未达标先修流程，再开板。 |
| **S1 有线功能原型** | 开发板、SPI 转接屏、实体大键、Windows 上位机 | 通过双会话上屏与回跳。方屏同时局刷时做至少 200 次按键操作，要求零丢键和零重复，并记录响应耗时。重复拔插 20 次并检查恢复和离线页。核对端到端跳转和上屏耗时。 |
| **S2 三模开发板验证** | 两块无线开发板验证接收器；键盘侧验证 BLE 和电源方案 | 三模各跑核心路径，切模与异常断开测试无粘键和动作重放。测试接收器重新插拔、BLE 休眠重连及 2.4G 干扰。分别记录输入、状态回传、重连耗时和待机／亮屏／使用时电流。 |
| **S3 首发工程样机** | 采购正式屏，冻结料号、天线、电池、充电和结构后画板 | 装配方运行离线产测并记录整机结果。开发方在实机跑三模与大键闭环，按 BR-05 单独验收首发语音。以实测电流和典型亮屏占空验证续航目标，复核金属外壳下的射频表现、配对安全、恢复烧录和实际报价。 |

**性能与价值验收。** S0 用现成键模拟大键，S1 用实体键，均从触发计时到正确终端可见并核对焦点，首轮目标 P95 ≤ 1 秒。S1 从受测 Agent 状态变化到方屏实机显示新卡片，首轮目标 P95 ≤ 2 秒。自动成功样本计算 P95，超时、失败与人工兜底单列，并继续执行零错跳和自动成功率门槛。S0 的模拟屏只计软件链路。S1 由同一用户在同类任务下对比手动切窗、桌面通知＋全局热键、实体方屏＋大键，记录耗时、漏处理和一周后的主动使用。

**无线放行。** S2 结束后，依据双向链路、功耗、样机报价和合规路径复核首发三模。分别核对键盘与接收器的实际射频参数是否符合微功率短距离设备目录。需核准时以官方流程和实际预检、整改、代理报价排期。

首板冻结前记录并确认三模各自的响应与重连目标、典型使用周期、可接受的电池容量与结构尺寸。S2 如未过关，继续用有线原型验证产品，保留三模首发目标并重新评估无线方案。正式采购以现货料号、参考设计和实测结果为准。

## 6. AI Coding 与工程交付

- 第一个实现阶段先提交 S0 Stage Spec，固定测试场景、验收口径和工作区范围。用真实脱敏 Hook 样本做状态重放，用模拟传输测试队列、过期事件和重连，再跑实机。模拟通过和实机通过分别记录。
- 实现时固定 .NET SDK、Node.js 依赖、Pico SDK 和 Nordic 工具链版本。提供 PowerShell 入口，把 `dotnet test`、扩展编译、`cmake --build`、`west build` 和产物位置纳入可复现的开发流程。首次烧录步骤、恢复入口和串口日志位置随版本记录。
- Codex、Claude Code 或 Cursor 可根据小型 Stage Spec 实现驱动适配、协议编解码和测试夹具。让工具输出构建与测试结果。窗口焦点、USB 枚举、射频、电流和手感用设备复核。
- 外包交付包含原理图和 PCB 源文件、Gerber、BOM、贴装坐标、结构 STEP、正式／产测固件、烧录恢复说明及逐台产测记录。KiCad 工程运行 ERC／DRC。所有 EDA 格式下，投单前核对 BOM 与 CPL 位号、正反面、贴装旋转及有极性器件方向，保存贴片预览确认记录。封装、天线净空、充电电路和装配干涉由工程师对照实物复核。
